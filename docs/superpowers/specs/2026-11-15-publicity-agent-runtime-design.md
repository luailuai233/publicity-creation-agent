# 热点驱动宣传创作工作台 Agent 重构设计

## 1. 意图与背景

本次重构以 `D:\aipm\MVP开发Plan.md` V3.0 为产品基准，把现有 Python Demo 从“用户逐页点击生成”的固定工作流改造成真正由单 Agent 驱动的宣传创作工作台。

用户只需要创建项目、分别提供活动资料与参考资料、填写创作目标并点击“开始自主创作”。Agent 随后读取持久化项目状态，制定可展示的简短计划，在白名单工具中选择下一步、保存结构化结果、判断是否继续或暂停，并自动完成策略、标题、大纲、正文与质量检查。用户只在关键事实冲突、必要资料缺失和最终导出时介入。

首版不连接外部模型 API。它使用确定性的 Mock Provider 模拟模型推理，但 Agent Runtime、工具选择、状态判断、暂停/恢复、调用限制、数据隔离、持久化和错误恢复均为真实实现。后续接入真实模型时只替换 Provider，不改变 Agent Runtime、工具、数据库和页面主流程。

## 2. 目标、非目标与反目标

### 2.1 P0 目标

- 单用户、无登录、本地桌面 Web Demo；
- 保留现有 FastAPI、Jinja/HTMX、SQLAlchemy/SQLite、复古桌面 UI 和六个功能页面；
- 首页/项目工作区提供创作目标、受众、语气、篇幅和“开始自主创作”；
- 新增单 Agent Runtime，真实读取项目状态并从六个白名单工具中选择下一步；
- 六个工具为资料解析、事实校验、案例分析、策略规划、内容生成和质量检查；
- 自动生成三个差异化策略，推荐并默认采用一个，用户可覆盖；
- 自动选择推荐标题，生成大纲和正文，不再等待用户逐步确认；
- 关键事实冲突或不可安全继续的缺失会令 Run 进入 `WAITING_USER`；
- 用户回答后从断点恢复，不重复已经成功且输入未变化的步骤；
- 质量检查后最多自动修订一次并复检；
- 完整保存 AgentRun、AgentStep、用户决定、工具摘要、草稿与检查结果；
- 页面展示阶段、工具名、结果摘要、待确认问题和失败原因，不展示隐藏推理；
- 保留事实/参考资料物理隔离和正文事实引用；
- 所有源码、数据库、上传、缓存、日志、测试、截图和导出仍限制在 `D:\aipm\demo`。

### 2.2 暂不实现

- 首版不调用真实 OpenAI 或其他模型 API；
- 不实现多 Agent、任意工具调用、任意网络访问、Shell 或模型直连数据库；
- 不实现登录、多用户协作、云队列、实时热点抓取或自动发布；
- 不让模型自行生成或执行 SQL；
- 不展示 chain-of-thought、系统提示词或模型密钥；
- 不删除六个页面，但它们改为可检查、纠正和覆盖 Agent 产物的工作台，不再构成必须手动点击的流水线。

### 2.3 反目标

- 不能只播放固定的“Agent 正在执行”文案而不读取真实项目状态；
- 不能把现有前端串联按钮改名为 Agent 后继续按固定脚本运行；
- 不能把参考案例事实混入活动事实库或正文生成输入；
- 不能在存在关键冲突时静默生成确定性陈述；
- 不能因工具失败丢失已经完成的结果；
- 不能把 Mock 结果冒充真实模型调用。

## 3. 方案选择

### 3.1 已选择：在现有 Python 工程上重构

保留成熟的资料、事实、案例、策略、草稿、检查、导出与复古 UI 实现，新增 Runtime、工具注册表和 Agent 状态页面，并把旧服务包装成可验证输入输出的 Agent 工具。这个方案复用已有测试和数据边界，能够把时间集中在“自主性与恢复能力”上。

### 3.2 未选择方案

1. **Next.js + Prisma 全量重建**：与原计划技术示例一致，但会重写现有上传、持久化、页面和测试，增加周期而不提高 Agent 核心验证价值。
2. **FastAPI + React 双栈重构**：交互扩展性更强，但首版的主要风险在 Runtime、事实约束和恢复，不在前端渲染能力。

## 4. 总体架构

```text
复古工作台 UI
  ├─ 项目目标与启动/暂停/取消/恢复
  ├─ Agent 状态面板与执行时间线
  └─ 六页产物检查与人工覆盖
           │
           ▼
Agent API ── Agent Runner ── Policy/Planner
                    │             │
                    │             └─ 读取 ProjectSnapshot，决定下一个 ToolCall
                    ▼
              Tool Registry
  ┌────────┬────────┬────────┬────────┬────────┬────────┐
  │资料解析│事实校验│案例分析│策略规划│内容生成│质量检查│
  └────────┴────────┴────────┴────────┴────────┴────────┘
                    │
        业务 Service + AIProvider 边界
                    │
     SQLite 项目记忆 + 项目内文件存储
```

Agent Runtime 不直接写业务表。每次工具调用都经过注册表，调用已有 Service，使用 Pydantic 输入输出 Schema，并在同一事务边界内保存结果与 `AgentStep` 摘要。

## 5. Agent 状态与持久化

### 5.1 新增实体

`AgentRun`：

- `id`, `project_id`, `status`, `goal`, `plan_summary`；
- `current_stage`, `tool_call_count`, `revision_count`；
- `max_tool_calls` 默认 12，`max_revisions` 默认 1；
- `waiting_reason`, `waiting_payload`, `error_code`；
- `cancel_requested`, `started_at`, `updated_at`, `ended_at`；
- 同一项目同一时间最多一个活动 Run。

`AgentStep`：

- `run_id`, `sequence`, `tool_name`, `status`；
- `input_fingerprint`，用于避免刷新或恢复后的重复执行；
- `input_summary`, `output_summary`，只存可展示摘要；
- `result_ref`，指向业务产物 ID，不复制原始全文；
- `retry_count`, `error_code`, `started_at`, `ended_at`。

`AgentMessage`：

- 保存 `PLAN`、`STATUS`、`QUESTION`、`USER_ANSWER`、`RESULT` 类型的可展示消息；
- 不保存隐藏推理，只保存短计划、事实问题、失败原因、完成摘要和用户答复。

项目新增创作目标字段；用户决定可保存在结构化 JSON 中，包括冲突裁决、策略覆盖、禁用表达和最终审核状态。

### 5.2 Run 状态

`QUEUED → RUNNING → WAITING_USER | COMPLETED | PARTIAL | FAILED | CANCELLED`

- `WAITING_USER` 只能由关键事实冲突、活动事实不足或必须由用户决定的隐私/身份问题触发；
- 单文件失败不会让整个 Run 失败；若仍有足够资料则记录警告并继续；
- 已生成部分产物但无法安全完成时使用 `PARTIAL`，并列出未完成步骤；
- 取消在工具边界生效，不中断数据库事务；
- 应用重启时，把遗留 `RUNNING` Run 放回 `QUEUED`，从最后一个成功步骤恢复。

用户主动暂停使用持久化的 `PAUSED` 状态；服务重启后保持暂停，只有用户点击恢复才继续。达到 12 次调用后 Run 进入 `PARTIAL`，重试会创建一个新的 Run 并获得新的 12 次预算，但复用输入指纹仍有效的既有产物，不从头重做。

### 5.3 自动确认与最小事实门槛

首版的“确认”表示通过程序可验证的来源与一致性门槛，不表示模型对现实真实性作绝对保证。事实只有同时满足以下条件才可由 Agent 标为 `CONFIRMED`：

- 至少关联一个活动资料 SourceChunk，且来源位置可展示；
- 不来自 ReferenceCase；
- 相同类型/主题下没有冲突候选；
- 内容不依赖图片人物身份猜测；
- 引语来自采访、发言稿或用户明确标注的引语来源；
- 抽取器置信提示达到工具 Schema 规定的阈值。

低置信、身份、精确数字/时间冲突和无来源事实保持 `PENDING` 或 `CONFLICT`。开始策略规划至少需要活动名称、一个可用的时间或场景事实，以及三个其他已确认事实；不满足时 Agent 进入 `WAITING_USER`，让用户从现有来源候选中确认、编辑，或补充带来源的文本。用户不能通过只输入一个无来源结论绕过来源门槛。

## 6. Planner 与工具选择

首版采用可测试的状态策略 Planner，而不是把六个工具写死为一次性脚本。每个决策周期都会重新读取 `ProjectSnapshot`，计算缺口并返回一个结构化决定：

```python
AgentDecision(
    action="CALL_TOOL" | "ASK_USER" | "COMPLETE" | "FAIL",
    tool_name="fact_validation" | None,
    reason_summary="存在尚未校验的活动资料",
    expected_artifacts=["fact_cards"],
)
```

决策优先级：

1. 校验运行限制、取消请求和活动项目；
2. 处理未解析的活动/参考资料；
3. 建立或刷新事实卡；
4. 对关键冲突或事实不足暂停提问；
5. 分析尚未分析的参考案例；若无参考资料，暂停询问，用户明确允许后才按通用原则继续；
6. 生成三个策略并自动选择 Provider 推荐项；
7. 生成推荐标题、大纲和正文；
8. 运行质量检查；
9. 若只有可自动修复的表达问题且尚未修订，调用一次内容修订并复检；
10. 产物完整时完成，否则标记部分完成或失败。

这不是固定流水线：Planner 基于当前缺口选择动作。已有且输入指纹未变化的成功产物会跳过；用户修改事实、参考分析或策略后，相应下游指纹失效，只重跑受影响部分。工具调用达到 12 次后停止并说明未完成项。

允许“无参考资料继续”的决定按项目保存，直到用户新增参考资料或主动撤销；全部参考资料均解析失败等同于无可用参考资料。该决定只允许策略工具使用内置通用写作原则，不允许生成任何活动事实。

人工修改始终高于 Agent 旧结果：用户确认/编辑的事实、策略覆盖、禁用表达和已手工修改的正文都带 revision。运行中的工具提交前若发现相关 revision 已变化，则放弃本次旧结果并重新规划；不会覆盖人工编辑。终态 Run 后的素材、事实、参考、目标或策略变更只标记对应下游产物为 `STALE`，由用户点击“重新自主创作”启动新 Run，不在后台擅自改写。人工正文修改后，自动重跑只执行质量检查；除非用户明确要求“按新条件重新生成正文”，否则不覆盖正文。

## 7. 六个白名单工具

所有工具实现统一接口：`name`、`input_model`、`output_model`、`can_run(snapshot)`、`execute(context, input)`。注册表拒绝未知工具名。

1. `parse_materials`：解析待处理的活动资料和参考输入，逐文件保存状态；失败互不影响。
2. `validate_facts`：从活动资料创建/合并事实卡、来源和冲突组；绝不读取 ReferenceCase 作为事实。
3. `analyze_references`：生成受众、钩子、情绪、结构、节奏、图片作用、迁移方法和禁用表达。
4. `plan_strategies`：只接收已确认事实、方法摘要和项目目标；生成三个差异策略，校验差异后保存推荐 ID 并默认选中。
5. `generate_content`：使用选定策略和当前已确认事实生成五个标题、推荐标题、大纲、正文和引用；支持 `mode=initial|revision`。
6. `check_quality`：执行确定性事实/冲突/隐私扫描和 Provider 补充检查；返回问题、严重性、位置、建议及是否可自动修复。

## 8. Mock Provider 与真实 API 接入

现有 `AIProvider` 继续作为模型边界，补充以下能力：

- 所有返回继续通过 Pydantic Schema 校验；
- Provider 返回推荐策略 ID、推荐标题和可自动修复标记；
- Mock Provider 依据输入状态产生确定性结果，并标记 `isDemo=true`；
- Provider 结构错误最多重试一次；再次失败由工具返回可恢复失败；
- Provider 不拥有数据库 Session、文件系统对象或任意工具执行权。

新增 Provider Factory，通过项目内 `.env` 选择：

```text
AI_PROVIDER=mock                 # 默认
AI_PROVIDER=openai_compatible    # 后续真实接入
AI_BASE_URL=https://.../v1
AI_API_KEY=...
AI_MODEL=...
```

真实接入只需要实现 `OpenAICompatibleProvider(AIProvider)`：把各方法的结构化输入发给兼容 Chat/Responses 接口，要求 JSON Schema 输出，转换为现有 `AIEnvelope`，并沿用超时、一次重试、来源 ID、Mock/真实标识和错误码约定。密钥只由服务端读取，不写数据库、日志、页面或导出。README 提供配置步骤和最小连通性检查，但本次交付默认测试不会访问网络。

本轮实现范围是 Provider Factory、完整接口契约、`.env.example` 和接入教程；不交付会发起真实网络请求的 Provider。`AI_PROVIDER=openai_compatible` 在未安装实现时必须启动失败并给出明确配置提示，不能静默回退或伪装成真实调用。

## 9. 用户体验改造

### 9.1 首页与项目工作区

- 创建项目后显示活动资料、参考资料和创作目标三个准备区；
- “开始自主创作”是唯一主 CTA；
- 启动后展示当前计划、六阶段状态、当前工具、结果摘要、警告和待确认问题；
- 提供暂停/取消；等待用户时提供结构化确认表单；完成后提供“审核最终稿”。

### 9.2 六个现有页面

- 素材页：上传、解析结果修正、事实确认和冲突处理；
- 灵感页：查看或修改案例分析，不再要求点击它才能进入策略；
- 策略页：展示三个方案、推荐理由和 Agent 默认选择，用户覆盖后使下游内容失效；
- 编辑页：直接展示 Agent 自动生成的标题、大纲和正文，允许编辑并自动保存；
- 检查页：展示检查、自动修订记录和导出门禁；
- Dock 仍允许自由进入各页，它们是产物工作区，不是执行步骤按钮。

旧的“分析案例并生成策略”“生成标题与大纲”等串联按钮从主流程移除；需要保留的人工重跑操作放在次级菜单，并明确其影响范围。

## 10. API

- `POST /api/projects/:id/agent-runs`：以项目目标启动 Run，立即返回 `runId`；
- `GET /api/agent-runs/:runId`：返回状态、计划、阶段、计数和等待问题；
- `GET /api/agent-runs/:runId/steps`：返回可展示的工具时间线；
- `POST /api/agent-runs/:runId/answers`：保存用户回答并恢复；
- `POST /api/agent-runs/:runId/pause`：在工具边界暂停；
- `POST /api/agent-runs/:runId/resume`：恢复暂停或可重试 Run；
- `POST /api/agent-runs/:runId/cancel`：设置取消请求；
- `POST /api/projects/:id/agent-runs/latest/retry`：从最后成功步骤重试失败运行。

API 使用现有 `{data, error, requestId}` 契约。前端以 1.5 秒轮询刷新，不引入 Redis、WebSocket 或外部队列。

## 11. 错误、恢复和并发

- 每个 Step 在执行前写入 `PROCESSING`，成功后在保存业务结果的同一事务中写 `DONE`；
- 相同 `run_id + tool_name + input_fingerprint` 的成功 Step 不重复执行；
- 同项目活动 Run 通过数据库唯一约束/应用锁限制为一个；
- 工具异常保存非敏感错误码，保留已有产物；可恢复错误允许重试；
- Run 恢复前重新生成 Snapshot，不能盲目沿用旧内存状态；
- 结构错误和暂时性 Provider 错误重试一次，业务冲突不自动重试；
- 检查失败显示“检查未完成”，绝不显示“通过”；
- Run 日志不保存素材全文、参考原文、提示词、密钥或隐藏推理。

### 11.1 完成与导出门禁

- 存在未解决的事实冲突、无来源关键事实、检查未完成或正文引用失效时，Run 不能 `COMPLETED`，导出也被阻止；
- 自动修订一次后仍有上述事实类阻断项时进入 `WAITING_USER` 或 `PARTIAL`；
- 相似表达和一般隐私提示不自动改写用户已审阅的事实。用户查看后可标记“已处理”或“知悉风险”；
- 只有当前 Draft revision 的质量检查有效，正文再次保存后旧检查立即标记 `STALE`；
- 无事实类阻断项时 Run 可 `COMPLETED`，但导出仍要求用户完成最终审核；
- 用户可以在明确确认后带着尚未关闭的非事实类高风险提示导出，导出记录保存确认时间和问题 ID；事实来源/冲突类问题不能通过确认绕过。

## 12. 测试与验收

### 12.1 单元测试

- Planner 针对不同 ProjectSnapshot 选择正确工具或暂停；
- 工具注册表拒绝未知工具，所有输入输出通过 Schema；
- 最大 12 次调用、单工具一次重试、最多一次修订；
- 指纹相同时跳过，事实/策略修改后仅失效下游；
- 推荐策略和标题自动采用，用户覆盖优先；
- 参考案例不能进入 FactCard 或正文事实输入。

### 12.2 集成测试

- 启动 Run 后自动连续调用至少两个工具；
- 事实冲突进入 `WAITING_USER`，回答后从断点继续；
- 重启恢复不重复已成功步骤；
- 工具失败保留中间结果并允许重试；
- 自动生成三个策略、推荐策略、标题、大纲、正文、引用和检查结果；
- 可自动修复问题只修订一次；
- 用户覆盖策略后正文与检查重新生成；
- Mock Provider 全链路不访问网络。

### 12.3 E2E 验收

覆盖开发计划 AC-01 至 AC-10，并新增：

- 用户只在首页启动，不点击六个工具按钮也能完成无冲突主链路；
- UI 时间线真实对应数据库 AgentStep；
- 冲突场景只要求一次关键确认；
- 页面刷新和服务重启后可恢复；
- 1440×900 与 1280×800 下状态面板、确认表单和最终稿可用；
- 所有测试、浏览器 profile、数据库、上传、导出和截图均在 `D:\aipm\demo`。

## 13. 迁移与兼容策略

- 新增 Alembic 迁移，不破坏现有项目、素材、事实、参考案例和草稿；
- 现有 Demo 种子升级为 Agent 演示项目，保留一个冲突场景和一个无冲突快速场景；
- 已有业务 Service 先通过适配器成为工具，避免大规模重写；
- 旧手动 API 可暂时保留供页面编辑和测试使用，但不再由主 CTA 串联；
- 旧版设计文档作为历史记录保留，新文档优先于旧文档中“必须手选策略/标题/大纲”的描述。

## 14. 实施顺序

1. 数据模型、迁移和 Agent Schema；
2. ProjectSnapshot、Planner、Tool Registry 与 Runtime；
3. 六个现有 Service 的工具适配与自动推荐/修订能力；
4. Agent API、进程内 Runner 和恢复；
5. 首页启动区、状态面板、时间线和确认 UI；
6. 六页从固定流程改为产物工作区；
7. Provider Factory 与真实 API 接入文档；
8. 单元、集成、E2E、D 盘边界和连续运行验收。

## 15. 成功判定

用户可以从一个已准备资料的项目输入创作目标，只点击一次“开始自主创作”，看到 Agent 根据项目真实状态调用工具并持续保存结果；无冲突时自动得到三个策略、推荐方案、推荐标题、大纲、带事实引用正文和质量检查；有冲突时准确暂停，用户确认后从断点继续；刷新或重启不会重复已完成步骤。所有 Mock 结果明确标识，切换到真实模型只需配置 Provider，而不需要重写 Agent 主流程。
