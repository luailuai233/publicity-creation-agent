# 热点驱动宣传创作工作台 Demo 设计

## 1. 意图与背景

本项目交付一个单用户、无登录、桌面端优先的本地 Web Demo。它面向需要把活动素材整理成可核验宣传长图文的内容编辑人员，重点证明以下闭环可以连续运行：

`创建任务 → 导入活动素材 → 确认事实 → 录入参考案例 → 拆解表达方法 → 选择创作策略 → 生成并编辑正文 → 检查风险 → 导出`

Demo 的价值不在于模拟“一键写稿”，而在于让用户在事实确认、策略选择和导出检查三个关键节点保留控制权。复古互联网编辑部界面用于增强识别度，但不得牺牲信息清晰度或延误主链路。

## 2. 已确认的实施路线

采用 **FastAPI + Jinja2/HTMX + SQLAlchemy/SQLite + Mock AI Provider**：

- FastAPI 同时承载服务端页面路由与内部 JSON API；
- Jinja2 生成页面，HTMX 负责局部刷新，少量项目内原生 JavaScript 负责自动保存、剪贴板和文件上传进度；
- SQLite 保存项目、素材、事实、参考案例、策略、稿件、检查问题和任务状态；
- SQLAlchemy 2 管理 ORM，Alembic 管理迁移；
- AI 能力通过 Python Protocol/抽象接口隔离，首版 Provider 返回通过 Pydantic 校验的结构化模拟结果；
- 模拟 AI 只替代外部模型推理，不替代产品状态流、数据约束、内部 API、持久化和错误处理；
- 不要求部署即可本地运行；保留 Docker 配置作为可选交付物；
- 后续接入真实模型时，只新增 Provider 实现并配置服务端密钥，不改业务页面和核心数据通道。

### 2.1 曾考虑的方案

1. **FastAPI + Jinja2/HTMX + SQLAlchemy/SQLite + Mock AI Provider（修订后已选）**：核心业务和服务端均使用 Python，页面只保留少量必要 JavaScript；便于用户后续理解和维护，同时能够实现真实产品链路。
2. **纯前端 + 浏览器存储**：速度快，但上传解析、服务端校验、Job 轮询和数据约束不真实，无法充分验证开发计划。
3. **FastAPI + React/TypeScript**：复杂界面开发能力更强，但用户仍需维护 TypeScript 前端，不符合此次技术偏好。

## 3. 目标、非目标与反目标

### 3.1 P0 目标

- 创建、恢复、打开示例和删除项目，刷新后状态不丢失；
- 导入 DOCX、PDF、TXT、常见图片及粘贴文本；
- 单文件上限 20 MB；每项目最多 30 个文件、素材文件总容量最多 200 MB；图片格式为 PNG、JPG/JPEG、WEBP；
- 每个文件独立显示处理状态，单文件失败不阻塞其他文件；
- 提取并编辑文本，形成带来源的事实卡、时间线和冲突组；
- 事实可确认、修改、作废，冲突必须人工解决；
- 参考案例与活动事实物理隔离，只将方法摘要用于策略生成；
- 产生三个实质不同的创作策略，并要求用户主动选定；
- 产生五个候选标题、大纲和可编辑正文；
- 正文只引用已确认事实，并保留事实引用关系；
- 检查无来源事实、事实冲突、近似表达和隐私风险；
- 导出 Markdown，支持复制纯文本；
- 六个页面共享同一复古桌面外壳，在 1440×900 和 1280×800 下可用；
- 提供完整脱敏示例项目和明确标记的 Mock/Demo 结果；
- 自动化测试覆盖核心规则、API 集成和主路径。

### 3.2 P1（仅在 P0 完成后）

- 段落级改写、内容锁定、版本恢复；
- 富文本复制、窗口最小化和最大化；
- 定制像素图标、AI 聊天气泡和更丰富动效。

### 3.3 明确不做

- 登录、权限、协作审批和多人实时编辑；
- 全网抓取、热点监控或第三方账号连接；
- 人脸识别、照片人物身份推断；
- 公众号自动发布或多平台排版；
- 自由拖拽窗口、窗口层叠管理器和桌面图标拖动；
- 阅读量预测、“爆款评分”或法律结论；
- 首版真实模型调用。

### 3.4 反目标

- 不能用静态页面跳转冒充业务链路；
- 不能把参考案例原文当作活动事实或直接送入正文生成；
- 不能让冲突事实或未确认事实悄悄进入正文；
- 不能让检查服务失败表现为“已通过”；
- 不能把 Demo 模拟结果伪装成真实 AI 返回；
- 不能因复古视觉牺牲正文可读性和主操作可见性。

## 4. 强制运行环境约束

用户要求项目产生的全部文件位于 `D:\aipm\demo`，不得把项目运行时产生的文件写入 C 盘。实现和文档均需遵守以下约定：

- 源码、Git 元数据、依赖目录、构建产物、SQLite 数据库、上传文件、导出文件、测试报告和截图全部位于 `D:\aipm\demo`；
- 项目提供 `scripts/setup.ps1`、`scripts/dev.ps1`、`scripts/test.ps1` 和 `scripts/e2e.ps1`，在启动子进程前设置项目专用环境变量；
- Python 虚拟环境位于 `D:\aipm\demo\.venv`；
- `PIP_CACHE_DIR` 指向 `D:\aipm\demo\.runtime\pip-cache`；
- `PYTHONPYCACHEPREFIX` 指向 `D:\aipm\demo\.runtime\pycache`；
- `PYTHONUSERBASE` 指向 `D:\aipm\demo\.runtime\python-user`；
- `TEMP` 与 `TMP` 指向 `D:\aipm\demo\.runtime\tmp`；
- `PLAYWRIGHT_BROWSERS_PATH` 指向 `D:\aipm\demo\.runtime\playwright-browsers`；
- SQLAlchemy 数据库 URL 指向 `D:\aipm\demo\storage\app.db`；
- 上传文件位于 `D:\aipm\demo\storage\projects\<projectId>`；
- 下载与演示导出默认写入 `D:\aipm\demo\exports`；
- 为避免浏览器默认下载目录落在 C 盘，P0 不触发浏览器文件下载；服务端生成 Markdown 到 `D:\aipm\demo\exports`，页面显示绝对路径并提供“复制纯文本”；
- pytest 缓存和测试报告保留在项目目录；
- `.runtime`、`.venv`、`storage` 中的运行数据、`exports` 和测试报告按用途加入 `.gitignore`，示例种子数据除外；
- HTMX 与必要前端脚本随项目静态文件提供，不依赖 CDN，也不引入 Node/npm 构建链；
- README 只推荐通过上述 PowerShell 脚本创建环境、启动、测试和运行 E2E，避免使用未重定向缓存的裸命令；
- 应用本身不读取或写入用户主目录、AppData 或系统临时目录。

已有 Python 解释器、浏览器或系统工具本身可以位于 C 盘，但本项目不得要求这些工具在运行期间向 C 盘创建项目缓存或用户数据。若第三方工具无法保证该约束，则不采用该工具或通过项目内环境变量重定向。

## 5. 用户体验与信息架构

### 5.1 全局框架

所有页面使用统一桌面外壳：52 px 顶栏、左侧 Dock、浅蓝点阵桌面、标准内容窗口和 44 px 底部任务栏。核心工作区使用固定 CSS Grid，不开发窗口拖拽。

Dock 顺序固定为：首页、素材、灵感、策略、编辑、检查。项目内页面显示项目名称、保存状态和后台任务摘要。每页最多一个粉色主 CTA，其他动作使用蓝色或灰色按钮。

### 5.2 页面流程

#### 首页 `/`

- 新建项目表单仅要求活动名称；受众、语气和篇幅可使用默认值；
- 显示最近项目、当前阶段、更新时间和继续入口；
- 提供“载入示例任务”；
- 删除项目需要确认，并级联清理其本地文件；
- 空状态仍保留明确的新建入口。

#### 素材库 `/project/[projectId]/materials`

- 三栏：分类树、素材列表、预览与可编辑解析文本；
- 支持文件选择和粘贴文本；文件限制为单文件 20 MB、每项目最多 30 个、总容量 200 MB，图片接受 PNG、JPG/JPEG、WEBP；
- 上传后为每个文件创建独立 Job，并显示队列、处理中、完成、待复核或失败；
- TXT 进行真实本地文本读取；DOCX 与文本型 PDF 使用本地解析库；图片和扫描件由 Mock Provider 返回明确标记的 OCR/场景摘要，结果可编辑；
- 解析结果可自动归类，用户可修改分类；
- 事实卡显示内容、类型、置信度、状态和来源数；
- 来源弹窗显示文件名、页码或段落以及原文片段；
- 冲突组需要用户选择一个值或手工填写结果；
- 删除素材后，失去全部来源的事实自动回到 PENDING。

#### 灵感拆解 `/project/[projectId]/inspiration`

- 使用三列等高窗口，1280 px 时仍保持横向三列，通过压缩间距和内容密度适配；
- 左列固定展示最多三个选中案例，可输入文本或上传截图；链接只保存标签和用户粘贴内容，不联网抓取；
- 中列展示钩子、情绪反差、叙事结构和图片作用四类机制；
- 右列展示可迁移方法、不可照搬内容、适配提醒和风险等级；
- 方法依据可追溯到参考案例片段，但这些片段不会进入 FactCard；
- 主 CTA 为“生成 3 个创作策略”。

#### 策略 `/project/[projectId]/strategy`

- 三个 ProposalWindow 并排展示人物故事型、反差成长型和现场纪实型；
- 每个策略展示受众、角度、开头、结构、使用事实、方法摘要、风险与标题方向；
- 程序校验至少两种叙事视角、两种开头、两种结构，且事实集合不完全相同；
- 策略只能引用 CONFIRMED 事实；
- 用户选中的策略用粉色标题栏表示，并可调整语气、篇幅和重点事实；
- 未选择策略不能进入正文生成。

#### 编辑器 `/project/[projectId]/editor`

- 左侧 220–240 px 事实素材抽屉，中间 Paper 正文，右侧 280–300 px 建议窗；
- 顶部包含标题、大纲、正文三个阶段标签；
- Mock Provider 生成五个候选标题和一个可编辑大纲；
- 用户确认标题与大纲后生成正文；
- 正文按 Markdown 文本编辑，P0 不引入复杂富文本编辑器；
- 关键事实以引用标记关联 DraftCitation，点击可查看来源；
- 编辑内容 2 秒防抖保存；
- 生成失败保留标题和大纲；
- 状态栏显示字数、引用事实数和最后保存时间。

#### 检查与导出 `/project/[projectId]/export`

- 左侧检查类别，中间问题列表，右侧正文预览；
- 规则检查先执行确定性扫描，Mock Provider 再补充近似表达和隐私风险示例；
- 问题分为 MISSING_SOURCE、FACT_CONFLICT、SIMILAR_EXPRESSION、PRIVACY_RISK；
- 检查失败时显示“检查未完成”，主 CTA 禁用；
- 未处理的高风险问题存在时，导出按钮要求显式确认；
- Markdown 导出由服务端依据当前稿件生成到 `D:\aipm\demo\exports` 并返回保存路径，不调用浏览器下载；纯文本复制由前端完成；
- 导出不得包含提示词、内部 ID、模型元数据或参考案例原文。

## 6. 数据与边界

核心实体沿用原计划：Project、Material、SourceChunk、FactCard、FactSource、TimelineItem、ReferenceCase、ReferenceAnalysis、Strategy、Draft、DraftCitation、QualityIssue、Job 和 EventLog。

### 6.1 强制数据规则

- Material 与 ReferenceCase 使用不同表，不建立内容复用关系；
- Strategy 和 Draft 只接收 `FactCard.status = CONFIRMED` 的事实 ID；
- 引语事实必须至少有一个来自采访或发言稿素材的 SourceChunk；
- CONFLICT 状态事实不能进入策略和正文；
- 删除 Material 时事务性删除 SourceChunk 与 FactSource；无剩余来源的 FactCard 改为 PENDING；
- 每次正文生成创建新 Draft 版本，编辑只更新当前版本；
- 项目删除同时删除数据库记录和项目存储目录，并做路径归属校验；
- UI 激活窗口、Tab 和临时选择保存在前端状态，不写业务数据库；
- EventLog 只存事件名、耗时、状态和非敏感计数，不存原始正文或素材全文。

### 6.2 默认值

- 新项目默认受众为“校园活动关注者”；
- 默认语气为“真实、温暖、克制”；
- 默认篇幅为 1200–1600 字；
- 默认只自动确认示例项目中明确带来源且无冲突的事实；普通用户上传所得事实初始为 PENDING；
- 示例项目包含一个时间冲突，以演示人工解决流程。

## 7. Mock AI 设计

### 7.1 Provider 接口

业务层只依赖统一 `AIProvider`，包含素材理解、事实抽取、案例拆解、策略生成、标题大纲、正文生成和质量检查方法。每个方法返回：

- `schemaVersion`；
- `result`；
- `warnings`；
- `sourceIds` 或 `factIds`；
- provider 名称、耗时、模拟 token 数、重试次数；
- `isDemo: true`。

所有返回在保存前必须经过对应 Pydantic Model。Provider 支持固定延迟、确定性种子和显式故障注入，以演示加载、失败、重试和降级状态。

### 7.2 模拟结果原则

- 示例项目使用预先审核的确定性结果，确保三次连续演示一致；
- 用户自建项目根据项目名、素材文本中的简单规则和已确认事实组装结果；
- 不从参考案例中提取或虚构活动事实；
- 不猜测图片人物身份；
- 若事实不足，策略与正文接口返回可解释的 NEEDS_REVIEW，而不是虚构细节；
- 模拟响应在 UI 中以“Demo 模拟结果”标识；
- 失败注入只影响当前 Job，不破坏已保存阶段结果。

## 8. 内部 API 与任务处理

内部 API 遵循原开发计划中的 REST 路径。所有写接口使用 Pydantic 校验请求，统一返回 `{ data, error, requestId }`。文件和生成类操作创建 Job，页面通过 HTMX 或少量原生 JavaScript 每 1.5 秒轮询。

Demo 使用进程内任务执行器：接口创建 Job 后安排异步处理并更新 SQLite 状态。应用重启时，将遗留 PROCESSING Job 标记为 FAILED/可重试，避免伪装为持续执行。单文件 Job 独立，批量上传不使用整体成功状态。

为了保持 Demo 简洁，不引入 Redis、消息队列、WebSocket 或独立服务。

## 9. 视觉与可访问性

- CSS Token 定义桌面蓝、窗口蓝灰、粉色主操作、边框、阴影、间距和字体；
- 点阵背景使用 CSS radial-gradient；正文容器不使用点阵；
- 图标使用 Lucide 加像素容器，不复制第三方品牌资产；
- 窗口使用一像素外框、内高光和统一阴影；
- 正文使用清晰的系统中文字体，不小于 12 px；
- 所有按钮有可见焦点、禁用态和 Tooltip；
- Tab、Dialog 和主表单支持键盘操作；
- 尊重 `prefers-reduced-motion`；
- 1280×800 下缩小 Dock、间距和装饰，不缩小正文字号，也不把灵感三窗改为上下排列。

## 10. 错误与恢复

- 上传、解析、生成和检查均有加载、空、失败、重试、待确认和完成状态；
- 单素材失败不会阻塞其他素材；
- Pydantic 校验失败自动以同一确定性输入重试一次，再失败则保存错误并允许人工编辑；
- 生成正文失败时不清除标题、大纲或已有稿件；
- 检查失败时禁止显示通过；
- 数据库或文件操作错误向用户提供可行动提示，并记录非敏感错误码；
- 示例任务可随时重置；提供只删除 Demo 数据的安全操作，不删除用户自建项目。
